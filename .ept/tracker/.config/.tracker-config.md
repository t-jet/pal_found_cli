## ID Counters

ID counters are stored in a dedicated structured file:

```yaml
id_counters_file: ".ept/tracker/.config/.id-counters.yaml"
```

**Usage**: Read `.config/.id-counters.yaml` to get current counters. After creating a ticket/link, increment the relevant counter in `.config/.id-counters.yaml`. Zero-pad to 3 digits for tickets (e.g., 001, 042, 123), 5 digits for links (e.g., LINK-00001).

## Link Management

```yaml
link_storage:
  file: ".config/.link-index.csv"
  format: "csv"
  status: "active"        # active | migrating | legacy
  location: ".ept/tracker/.config/"    # Config subfolder of tracker
  
# link_types and link_roles_mapping: see .config/.workflow.yaml (link_types section)

link_consistency:
  validation_enabled: true
  validation_frequency: "weekly"
  auto_repair: true       # Repair orphaned/broken links
  
link_operations:
  atomic: true            # All operations are atomic
  locking: true           # File locking during writes
  backup_on_update: false # Backup before each update (set true for safety)
```

**Usage**:

- All relationship links stored in `.ept/tracker/.config/.link-index.csv`
- Update `link_id_counter` (in id_counters section) after creating each link
- Migration from links.md files completed in v2.4 (TASK-031/032)

## Folder Structure

```yaml
folder_structure:
  root_level:
    - .config/             # Configuration subfolder (NEW in v3.4)
    - .instructions/       # Ticket type handling algorithms (YAML)
    - README.md            # User guide
    - FEATURE-XXX/         # Feature Request folders
    - EPIC-XXX/            # Epic folders (independent, linked to Features)
    - TASK-XXX/            # Task folders (general-purpose)
    - BUG-XXX/             # Production/UAT Bug folders
    - RESOURCE-REQ-XXX/    # Resource/Agent Request folders
  
  config_folder_contents:
    - .link-index.csv      # Centralized link storage
    - .index.csv           # Ticket index
    - .tracker-config.md   # This configuration file
    - .id-counters.yaml    # ID counters (structured, separate file)
    - .workflow.yaml       # Workflow specification (fields, ticket types, link types)
  
  ticket_folder_contents:
    - ticket.md            # ALL ticket types — single consistent content filename
    - comments/            # One file per comment: yyyymmdd-hhmmss-author.md
  
  task_children:
    - WORK-XXX/           # Work Item sub-tasks (for Task decomposition)
    - QUESTION-XXX/       # Question sub-task (can be child of any task/sub-task)
  
  feature_request_children:
    - BA-ANA-XXX/         # BA Analysis sub-tasks (ANALYSIS stage)
    - BA-DES-XXX/         # BA Design sub-tasks (DESIGN stage)
    - SA-ANA-XXX/         # SA Analysis sub-tasks (ANALYSIS stage)
    - SA-DES-XXX/         # SA Design sub-tasks (DESIGN stage)
    - UX-ANA-XXX/         # UX Analysis sub-tasks (ANALYSIS stage)
    - UX-DES-XXX/         # UX Design sub-tasks (DESIGN stage)
    - DEV-STORY-XXX/      # Developer Stories (nested in Feature, not Epic)
  
  developer_story_children:
    - DESIGN-XXX/         # Design sub-task (grooming/estimation)
    - DEV-XXX/            # Development sub-task
    - UNITTEST-XXX/       # UnitTest sub-task
    - CODEREVIEW-XXX/     # CodeReview sub-task
    - TESTCASE-XXX/       # TestCase sub-task
    - TESTEXEC-XXX/       # TestExec sub-task
    - DEVOPS-XXX/         # DevOps sub-task
    - BUG-SUB-XXX/        # Bug sub-task (found during QA)
    - QUESTION-XXX/       # Question sub-task (can be child of any task/sub-task)
  
  any_task_children:
    - QUESTION-XXX/       # Questions can be children of any task or sub-task
```

**Key Principle**: Developer Stories are physically nested under Feature Requests, NOT under Epics. Epics live at root level and are linked to Stories via "Epic Link" field.

## Link Types

### Hierarchical Links (via frontmatter fields)

```yaml
hierarchical_relationships:
  - type: "parent"
    description: "Parent ticket ID (folder location for physical nesting)"
    examples:
      - "Developer Story → parent: FEATURE-001 (physically nested in Feature folder)"
      - "Sub-Task → parent: DEV-STORY-001 or parent: DEV-001 (nested)"
      - "Question → parent: <any-ticket-id> (nested as child)"
  
  - type: "epic"
    description: "Epic Link field (logical grouping, NOT physical nesting)"
    examples:
      - "Developer Story → epic: EPIC-001 (for organizational purposes)"
  
  - type: "feature_request"
    description: "Feature Request this ticket implements/belongs to"
    examples:
      - "Epic → feature_request: FEATURE-001 (linked)"
      - "Developer Story → feature_request: FEATURE-001 (same as parent)"
```

> **Note**: Relationship link type definitions (types, roles, descriptions, usage) are maintained in `.workflow.yaml` (`link_types` section).

### Link Consistency and Validation

With centralized storage in `.link-index.csv`, consistency is inherently maintained:

```yaml
link_consistency:
  enforcement: "strict"
  single_source_of_truth: true  # No synchronization needed between files
  atomic_operations: true       # All link CRUD operations are atomic
  foreign_key_validation: true  # All referenced tickets must exist
  uniqueness_constraint: true   # No duplicate links (same source, target, type)
  
  link_creation:
    steps:
      - "1. Validate both tickets exist"
      - "2. Check link_type is valid"
      - "3. Check for duplicate links"
      - "4. Generate next link_id from counter"
      - "5. Append row to .config/.link-index.csv"
      - "6. Update link counter in .config/.id-counters.yaml"
      - "7. Update timestamps on both tickets"
    rollback_on_failure: true
    
  link_deletion:
    steps:
      - "1. Find link by link_id in .config/.link-index.csv"
      - "2. Remove row from CSV (rewrite file)"
      - "3. Update timestamps on both tickets"
      - "4. Add comments if deletion is significant"
    atomic: true
    
  link_update:
    process: "Delete old link + Create new link (preserving created timestamp)"
    atomic: true
    comment: "Add comment explaining change"
  
  validation:
    frequency: "Weekly (recommended)"
    checks:
      - "All source_ticket and target_ticket exist"
      - "No duplicate link_ids"
      - "No duplicate links (same source, target, type)"
      - "All link_types are valid"
      - "Orphaned links detected and reported"
    
  auto_repair:
    enabled: true
    safe_operations:
      - "Remove links where both tickets don't exist (orphaned)"
      - "Fix malformed link_ids"
      - "Remove duplicate links"
    manual_review_required:
      - "Links with invalid link_type"
      - "Links where one ticket exists but other doesn't"
      - "Circular dependencies"
```

  - id
  - type
  - title
  - status
  - priority
  - assignee
  - reporter

  - "Append row when ticket created"
  - "Update row when ticket modified"
  - "Mark deleted or remove when ticket closed/archived"
