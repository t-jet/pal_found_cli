### 🔴 CRITICAL-2: `_invoke` is `async` but Wrapped in `run_in_executor`\
\
**File**: `foundry_datasets_cli.py`, line ~420\
**Functions**: `_invoke()` (line ~106), `_invoke_async()` (line ~417)\
\
```python\
# _invoke is declared as async and uses `await`:\
async def _invoke(...) -> Any:\
    ...\
    return await client.create(...)  # uses await\
\
# But _invoke_async wraps it in run_in_executor:\
return await loop.run_in_executor(None, lambda: _invoke(...))\
```\
\
`run_in_executor` runs the callable in a thread pool executor. An `async` function called from a thread pool executor has no running event loop in that thread, so `await` will fail with `RuntimeError: no running event loop`.\
\
**Impact**: Even if the `timeout` bug were fixed, the async/executor pattern is fundamentally broken. `_invoke` is already async and should be called directly with `await`, not through `run_in_executor`.\
\
**Fix**: Either:\
- **Option A** (preferred): Call `_invoke` directly as async: `return await _invoke(resource, operation, client, args, timeout)`\
- **Option B**: Make `_invoke` synchronous and keep `run_in_executor`\
\
**Architecture Alignment**: Per SAD-001, async discipline requires `asyncio.run()` as entry point and proper async/await throughout. Option A is the correct approach.\

### 🟡 WARNING-1: `RetryHandler` Imported but Never Used (ADR-002 Violation)\
\
**File**: `foundry_datasets_cli.py`, line ~45\
\
```python\
from foundry_cli.common.retry import RetryHandler  # imported but never used\
```\
\
Per ADR-002, all API calls must use exponential backoff with jitter retry logic. The `main()` function has no retry wrapper around `_invoke_async`. The `RetryHandler` class in `src/foundry_cli/common/retry.py` supports both decorator and context manager patterns.\
\
**Impact**: No transient error recovery. Network blips, rate limits, or temporary server errors will cause immediate failure instead of retrying with backoff.\
\
**Fix**: Wrap the operation invocation with `RetryHandler` context manager or decorator.\

### 🟡 WARNING-2: `timeout` Never Extracted from Args or Config\
\
**File**: `foundry_datasets_cli.py`, line ~353-380\
\
In `main()`, the `timeout` parameter is never extracted before passing to `_invoke_async`:\
\
```python\
# In main():\
result = await _invoke_async(resource, operation, client, args)\
# ^-- no timeout parameter, and _invoke_async doesn't extract it either\
```\
\
Per ADR-002, a default timeout (30s) should be applied from `cfg.timeout` if not explicitly provided via `--timeout`.\
\
**Impact**: SDK calls receive `None` as timeout, potentially hanging indefinitely.\
\
**Fix**: Extract timeout before invocation:\
```python\
timeout = getattr(args, "timeout") or cfg.timeout\
```\
