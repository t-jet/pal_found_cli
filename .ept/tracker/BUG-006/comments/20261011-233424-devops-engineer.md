## In Progress evidence (BUG-006)

### Root cause confirmed: the scanner pulls the vulnerable package

- Controlling package is **safety itself** (the scanner), not the project. CI step log of job 112150492418 shows installation of the scanner: pip install bandit safety and the line Collecting nltk>=3.9 (from safety); resolved set includes 
ltk-3.10.3.
- Confirmed locally (fresh venv): pip show nltk -> Required-by: safety; safety.requires contains 
ltk>=3.9.
- pal_found_cli_tool/pyproject.toml declares no 
ltk dependency (oundry-platform-sdk, python-dotenv, equests; dev extras: pytest, mypy, ruff, bandit). The finding is about the CI scanning environment, not shipped code.

### Scope of the finding

- Only SFTY-20260902-58666 (CVE-2026-81726, path traversal) applies to 
ltk 3.10.3. Reproduced with a requirement scan of 
ltk==3.10.3: 1 vulnerability (the same ID).

### No fixed release exists

- Latest stable 
ltk on PyPI is 3.10.3 (the vulnerable version; advisory affects <=3.10.3).
- Latest safety on PyPI is 3.8.1 and still requires 
ltk>=3.9.
- Therefore the finding cannot be remediated by upgrading a dependency.

### Environment

- Repo 	-jet/pal_found_cli_tool, workflow .github/workflows/ci.yml, job security-scan; runner ubuntu-latest, Python 3.11, safety 3.8.1.

### Expected vs actual

- Expected: dependency scan passes with no unremediated HIGH/CRITICAL findings; Bandit HIGH gate stays enforced.
- Actual: scan exits 64 on the 
ltk advisory; Build Package reported skipped (
eeds: security-scan).

### Decision

- Because no fixed release exists, apply a documented, time-bound suppression in a committed policy file (pal_found_cli_tool/.safety-policy.yml) with reason and expiry, instead of an inline --ignore. continue-on-vulnerability-error: False keeps the scan blocking for any other finding. Bandit gate is unchanged.
