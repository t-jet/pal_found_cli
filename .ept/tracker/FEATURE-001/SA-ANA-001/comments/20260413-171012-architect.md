## Architecture Approach

### Affected Services and Interfaces

| Service / Interface | Role |
|---|---|
| Palantir Foundry API v2 | Target API — 20 namespaces, 355 operations |
| `foundry-platform-python` SDK | Python SDK wrapping API v2; `AsyncFoundryClient` used for all calls |
| VS Code Skill Runner | Host environment executing CLI skills via subprocess |
| Custom Agent Orchestrators | Any agent framework invoking CLI via subprocess |
| `.env` file | Configuration surface — credentials, access control flags, env var overrides |
| `.foundry-data/` directory | Session file persistence (AIP Agents stateful interactions) |
| stderr / stdout | Inter-process communication channel: JSON/TOON on stdout; structured logs on stderr |

### Technology Stack

| Layer | Technology | Rationale |
|---|---|---|
| Language | Python 3.10-3.12 | Matches SDK requirement; avoids 3.13 breaking changes (deferred — ADR pending) |
| SDK | `foundry-platform-python` | Only supported client library for Foundry API v2 |
| Async execution | `asyncio.run()` per invocation | No shared event loop; stateless per call (AC-4) |
| Output formatting | `toon >=0.9,<1.0` (TOON) + stdlib JSON | TOON for columnar arrays; JSON for structured objects |
| Config loading | `python-dotenv` | `.env` file loading; search path per ADR-006 |
| CLI framework | `click` | Consistent with existing SDK CLI; subcommand per operation |
| Auth | `UserTokenAuth` | Only mechanism available without OAuth2 flow |

### General Implementation Approach

- **21 skill packages**: 20 namespace-specific + 1 general Foundry knowledge skill
- **Shared module**: `_foundry_cli_common.py` — single source of truth for auth, config, access control, output formatting, retry, pagination, session management, binary download, tracing. Copied (not imported) into each skill at build time.
- **Per-invocation model**: no daemon; no persistent process; each subprocess call is self-contained
- **Access control**: 8-step precedence matrix (FOUNDRY_ACCESS_TIER -> namespace flags -> operation flags). Runs before any SDK call.
- **8 EPICs, 23 DEV-STORYs** defined in SAD-001 section 10 implementation roadmap

### General Migration Approach

Greenfield implementation — no migration from existing systems required. The SDK's own Click CLI is explicitly **out of scope** per FR-02 resolution. SDK version pinned in-repo; future SDK upgrades require explicit review and re-enumeration of operations.

### Key Architectural Decisions (ADRs)

| ADR | Decision |
|---|---|
| ADR-001 | Exit code taxonomy: 0=success, 1=usage error, 2=auth error, 3=access denied, 4=not found, 5=server error, 6=timeout, 7=format error |
| ADR-002 | Timeout defaults: 30s connect, 300s read for binary ops; configurable per operation |
| ADR-003 | Streams batch strategy: paginate all stream reads; no server-sent event streaming in MVP |
| ADR-004 | Format auto-selection: TOON for uniform arrays >=2 rows; JSON otherwise |
| ADR-005 | Log format: structured JSON on stderr with level, timestamp, operation, correlation_id |
| ADR-006 | .env search path: cwd -> $HOME -> $XDG_CONFIG_HOME/foundry -> /etc/foundry |
| ADR-007 | Operation-level READONLY is independent — namespace READONLY does not override operation-level setting |

### Risks

Key risks documented in SAD-001 section 11: TOON library API instability, SDK version breaks, `geo`/`core` namespace exclusion, FOUNDRY_TOKEN rotation gap, Windows SIGTERM handling.
