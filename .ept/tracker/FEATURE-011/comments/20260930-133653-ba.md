Business case:
Skills must use only the packaged pal-found-* CLI interface and contain no separate python scripts. Any additional Python code / command implementations must live in the tool (pal_found_cli_tool). Users must not need Python knowledge.

Verified repo state (2026-09-30):
- pal_found_cli_tool/pyproject.toml already exposes all 18 pal-found-* console entry points, including pal-found-datasets and pal-found-ontologies.
- pal_found_cli_skills/.agents/skills/pal-found-* (18 folders) each still ship scripts/pal_found_*_cli.py launchers; 16 are thin wrappers importing build_parser/console_main/main from the tool; 2 (datasets ~347 lines, ontologies ~214 lines) carry full standalone parser + business logic.
- SKILL.md files instruct users to run 'python pal_found_*_cli.py ...' directly.

Epic linkage decision:
- This is a NEW cross-cutting requirement, not covered by an existing Epic.
- EPIC-009 (harness-agnostic distribution / self-contained content) and EPIC-010 (public repos / PyPI / conda distribution) are both Done and archived; they established the distribution mechanics but did not require doc-only skills or removal of the scripts/ layer.
- This feature changes the delivered skill-content model (skills become documentation-only) and migrates two command implementations into the tool. It warrants a NEW Epic (BA/Architect will create at the start of design).
- As no Epic yet exists, no Epic link is established in this step; will be added once the new Epic is created.

Proposed scope:
1. Retire/remove the scripts/ launcher layer from all skills that are thin wrappers (16), making each skill consist solely of SKILL.md that invokes the packaged pal-found-* command.
2. Relocate the two standalone implementations (datasets, ontologies) business logic into the tool if duplicated/divergent, and make those skills doc-only.
3. Rewrite every SKILL.md so command examples use the installed pal-found-* command, not 'python pal_found_*_cli.py'.
4. Tool-side: ensure pal-found-datasets and pal-found-ontologies expose the full operation parity the skills document today.
5. Update distribution/onboarding docs and any evidence that assumes scripts/ exists.

Open questions (Address to Project Owner / Architect in analysis):
- Q1: Should the 16 thin-wrapper launch scripts be deleted outright or kept as undocumented legacy until a release deprecation cycle? (default: delete from the public skills repo per owner requirement)
- Q2: Are pal-found-datasets and pal-found-ontologies skill scripts duplicate/divergent from the tool modules? Confirm before migrating. (Architect)
- Q3: Does every skill user have a supported install path for pal-found-* commands (pip/conda) so a doc-only skill is usable without Python knowledge? 

Acceptance / evaluation criteria for Project Owner confirmation:
- No .py files remain under .agents/skills/ in the delivered skills repo.
- Every skill SKILL.md invokes the packaged pal-found-* command; no 'python ...cli.py' invocation remains.
- All 18 pal-found-* commands are installed and runnable from the tool with full operation parity documented by the skills.
- A fresh clone + package install yields all skills usable without writing or running Python.
