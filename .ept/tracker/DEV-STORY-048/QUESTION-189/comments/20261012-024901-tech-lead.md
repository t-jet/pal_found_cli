## Ruling

**The executable fixture must not ship in a distributed skill folder.** It is legitimate QA evidence, not a reader artifact, so it moves out of `.agents/skills/pal-found-data-health` into maintainer test fixtures, and the reader instruction becomes documentation only.

## Research done

- SA-DES-012 section 1.1: a skill folder contains documentation only; section 2: no executable script belongs in a distributed skill folder; section 5 local-distribution gate: no script files or stale launcher commands.
- SA-DES-013 section 3: the distribution is 20 Markdown skills. SA-DES-014 governs the separate `pal-found-dev` knowledge skill.
- Folder inventory (`git -C pal_found_cli_skills ls-files`): of the 18 CLI namespace skills, `pal-found-data-health` is the ONLY one with an `examples/` dir or any non-Markdown asset. The other 17 CLI skills are Markdown only. `pal-found-dev` legitimately ships 493 example files (including `.py`) under its own FEATURE-013/FEATURE-015 design, so it is out of scope here.
- The 16 JSON payloads duplicate content already inline in `references/check-config/*.md` (for example `buildStatus.md` carries the complete create and replace JSON), so no reader-only fact is lost by moving them.
- The `.py` is a QA offline-validation harness recorded green (exit 0) in `maintainer/development-author-source-evidence.json`. It is not referenced by any reader operation record and is not executed by the test suite.
- No approved requirement in `.ept/docs` mandates shipping offline payloads inside the data-health skill. Offline usability is satisfied by the complete inline JSON examples plus the installed CLI.

## Answer (option a)

The payloads and script are required QA artifacts, but they must be expressed as documented static examples rather than executed from inside the skill folder. The QA harness is preserved under `tests/fixtures/offline/data-health`, which is the approved maintainer fixture area and the folder the topic-acceptance runner already stages.
