### Review Checklist and Findings

#### A. ConfigLoader (ADR-006 Compliance)
- [x] **ADR-006 search path**: Decision is clear and well-justified -- explicit override > git root walk (20-level cap) > CWD fallback > env-vars-only. Home-dir exclusion is a deliberate security decision.
- [x] **load_dotenv(override=False)**: Correct -- shell env vars take precedence as required.
- [x] **ConfigurationError on missing explicit env file**: ADR-006 mandates exit code 9, which maps to ConfigurationError per ADR-001. Consistent.
- [x] **Typed accessors**: get_str(), get_bool(), get_int(), get_float(), get_enum() -- reasonable API surface. Note: get_bool() needs explicit truthy/falsy parsing (e.g., str().lower() in ('true','1','yes')).
- [WARNING FINDING] **CWD fallback ambiguity**: ADR-006 says "load .env from CWD itself" for non-git deployments, but does not specify whether the CLI script's directory or the process CWD is used. Since the CLI is subprocess-invoked, CWD is what the agent sets -- this is correct, but the implementation must NOT use `__file__` directory as anchor (ADR-006 explicitly rejects this). **Action**: Validate implementation uses Path.cwd() not Path(__file__).parent.

#### B. AuthProvider (SAD-001 Layered Security)
- [x] **Credential resolution from config**: SAD-001 states auth is the first layer. AuthProvider must fail before any SDK client is created.
- [x] **UserTokenAuth construction**: Matches SRS-001 definition (static bearer token).
- [x] **No credential logging**: SAD-001 cross-cutting concern #3 (layered security) and SRS-001 security constraint. CRITICAL -- implementation must audit all print(), logging.info(), logging.debug() calls.
- [WARNING FINDING] **FOUNDRY_TOKEN vs FOUNDRY_HOSTNAME handling**: ADR-001 exit code taxonomy lists exit code 2 for AuthenticationError (missing/invalid token) and exit code 9 for ConfigurationError (missing config). AuthProvider needs to distinguish: is FOUNDRY_TOKEN absent because of a misconfiguration (exit 9) or an auth failure at the SDK level (exit 2)? **Recommendation**: Missing FOUNDRY_TOKEN = exit 9 (config issue); invalid token format or SDK auth failure = exit 2.
- [WARNING FINDING] **Token validation timing**: SAD-001 C4 Level 2 shows AuthProvider -> SDK -> API flow. The token should be validated *before* constructing the SDK client (fail-fast principle). Implementation must not attempt SDK authentication -- that is the SDK's job. AuthProvider's job is to ensure a non-empty token exists.

#### C. AsyncClientFactory (SAD-001 Stateless Design)
- [x] **Stateless per invocation**: SAD-001 architecture principle: "No persistent processes; no daemon; stateless per invocation." Factory creates fresh client each call. Consistent.
- [x] **ConfigLoader as dependency**: Constructor injection is the correct pattern -- enables testability and loose coupling.
- [x] **Attribution header injection**: ENABLE_ATTRIBUTION=true gating per SAD-001 F-ATTR function. Must be conditional and header-only.
- [WARNING FINDING] **Client lifetime management**: Since each invocation creates a new AsyncFoundryClient, the factory should ensure proper async context manager usage (async with) to guarantee connection cleanup. Missing __aenter__/__aexit__ patterns could leak TCP connections. **Action**: Verify implementation uses `async with` or explicit close() in all invocation paths.
- [WARNING FINDING] **Error propagation chain**: ConfigLoader -> AuthProvider -> AsyncClientFactory -> SDK. Each layer must propagate structured JSON errors (per ADR-001 + SRS-001 FR-ERR-2) with correct exit codes. **Risk**: If AuthProvider raises ConfigurationError (exit 9) but AsyncClientFactory catches and re-raises as a different code, the chain breaks.
