### 1. Documentation Review Summary

#### ADR-006 — .env File Search Path
- **Key finding:** Search order is strict: explicit override -> git root .env -> CWD fallback -> env vars only. No home-dir fallback.
- **Test implication:** Must test all 4 search path stages. Git root detection requires temp git repos in fixtures. Explicit override must fail with exit 9 if file missing.
- **Critical path:** The 
o .env found path is NOT an error — must verify CLI continues with env vars only.

#### SRS-001 — Software Requirements Specification
- **FR-AUTH-1/FR-AUTH-2:** Auth must use UserTokenAuth only; missing FOUNDRY_TOKEN -> exit code 9.
- **DCC-4:** CLI contract: exit 0 on success, non-zero on error; stdout = data, stderr = metadata/diagnostics.
- **Test implication:** All test assertions must verify exit codes AND output channels (stdout/stderr separation).

#### SAD-001 — Solution Architecture Document
- **C4 Component Diagram:** ConfigLoader -> AuthProvider -> AsyncClientFactory is the strict invocation chain.
- **Sequence flow:** ConfigLoader is called first; AuthProvider depends on ConfigLoader output; AsyncClientFactory depends on both.
- **Test implication:** Integration tests must validate the full chain, not just isolated components.

### 2. Test Design Strategy

#### Layer 1: Unit-Level Component Tests (Isolated)
- **ConfigLoader:** Mock filesystem + python-dotenv. Test each search path stage independently.
  - Git root detection: Create temp git repo, place .env at root, verify discovery from subdirectories
  - CWD fallback: Create temp dir without .git, verify .env from CWD is loaded
  - Explicit override: Test valid path loaded; test missing path returns exit 9
  - Env var precedence: Set env var + .env key, verify env var wins (override=False behavior)
- **AuthProvider:** Mock UserTokenAuth class. Test token resolution from config, validation, hostname resolution.
- **AsyncClientFactory:** Mock AsyncFoundryClient. Test instantiation with valid/missing token, attribution header injection.

#### Layer 2: Integration Tests (Component Chain)
- Full chain: ConfigLoader -> AuthProvider -> AsyncClientFactory -> API call
- Partial chain failures: ConfigLoader OK, AuthProvider fails; AuthProvider OK, Factory fails
- Verify error serialization through the full chain (ErrorSerializer integration)

#### Layer 3: E2E Scenario Tests (Real-ish Environment)
- Use temp .env files + mocked SDK calls (no real API connection)
- Full invocation flow with success and all documented failure paths
- Security validation: Verify no credentials in logs, stdout, stderr, or temp files

#### Layer 4: Security Tests
- Credential leakage audit: Search all outputs for FOUNDRY_TOKEN patterns
- Log sanitization: Verify LogSetup does not expose tokens in NDJSON logs
- Access control: Verify tokens are never written to .foundry-data/ directory
