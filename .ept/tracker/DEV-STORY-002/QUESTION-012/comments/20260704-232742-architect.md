# Architect Decision — QUESTION-012

## Decision

**Option (a): Add the `toon-python` dependency (`>=0.9,<1.0`) and migrate `_format_toon()` to call `toon.from_list()`.** Reject options (b) and (c).

## Rationale

1. **The library is the contract, stated in three independent artifacts.**
   - **SRS line 140:** explicit dependency pin `toon-python >=0.9,<1.0` (installed from `git+https://github.com/toon-format/toon-python.git`).
   - **SRS C-2 (Technical Constraint):** "TOON library pinned `>=0.9,<1.0`; air-gap environments require private mirror" — treats the library as a fixed technical constraint, not an option.
   - **SRS OI-6 (Open Issue):** "TOON library installation in air-gapped environments" assigned to DevOps — a known follow-up.
   - **ADR-004 §Consequences:** "dispatching to `toon.from_list()` or `json.dumps()`" — names the library API directly.
   - **ADR-004 §References:** "`toon-python` library documentation".
2. **The hand-rolled renderer is a TOON-spec compliance risk.** TOON is a defined format (Tabular Object Output Notation); a custom renderer will diverge on edge cases (column-width algorithm, escape rules for embedded `|`/newlines, null rendering, unicode width). Downstream agents that parse TOON per the spec will break on the hand-rolled output. The library is the canonical reference implementation.
3. **Option (b) (keep hand-rolled, update AC) would require:**
   - Rewriting SRS line 140, SRS C-2, SRS OI-6, ADR-004 §Consequences, ADR-004 §References, and ADR-004 §Alternatives (which explicitly rejected library-fallback as brittle).
   - Replacing a customer-acknowledged technical constraint with an internal choice — needs Product Owner sign-off.
   - Owning TOON-spec compliance forever — a hidden maintenance tax.
   This is far more expensive than adopting the library and contradicts multiple accepted ADRs.
4. **Option (c) (defer to follow-up story) is rejected for v1.** TOON output is part of the public output contract (FR-OUT-5 through FR-OUT-7); shipping a non-compliant renderer in v1 and "fixing it later" creates a broken contract that agents will already depend on. The cost of migration only grows.

## Sub-decisions for the implementer

- **Dependency declaration:** Add to `pyproject.toml` `[project] dependencies`:
  ```toml
  "toon-python>=0.9,<1.0"
  ```
  Source per SRS line 140: install from `git+https://github.com/toon-format/toon-python.git` if not on PyPI; verify whether a PyPI release exists at implementation time and prefer PyPI if available. If git-only, document the index in `pyproject.toml` and flag for DevOps (OI-6).
- **API usage:** Replace `_format_toon()` body with `return toon.from_list(data)` (per ADR-004 §Consequences). Pre-validation (uniform-array check, error-envelope routing) already lives in `select_format()` and must be preserved — ADR-004 §Alternatives explicitly rejected "always call library and fall back" as brittle.
- **Error handling:** `toon.from_list()` raises on non-uniform input; the auto-selection algorithm MUST guarantee uniformity before calling it. Add a defensive `try/except` that logs and falls back to JSON only if a uniform-array invariant is violated at runtime (defensive coding, not a primary path).
- **Tests:** Existing TOON tests must be re-verified against `toon-python`'s actual output format (column widths, header rendering, null/escape behavior). Any test that asserted hand-rolled output text must be updated to assert against `toon-python` output. This is contract conformance, not test fragility.
- **Air-gap (OI-6):** Out of scope for this story. DevOps owns the mirror setup; the `pyproject.toml` declaration is the trigger. Add a comment to OI-6 (or its successor ticket) noting the dependency is now declared.

## Impact

- Code: small (single method + 1 dependency line).
- Tests: medium (TOON output fixtures may need updates to match canonical library output).
- Packaging: new runtime dependency; air-gap deployment blocked until OI-6 resolved by DevOps.
- Risk: Medium — TOON output text will change (hand-rolled → canonical). Any downstream consumer that pinned to hand-rolled output breaks; acceptable in v1 since no consumers exist yet.
- Estimate: 0.5 day for developer + 0.5 day for qa-engineer fixture updates.
