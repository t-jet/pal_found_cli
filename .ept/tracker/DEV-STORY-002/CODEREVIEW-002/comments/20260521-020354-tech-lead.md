## MAJOR FINDINGS

### MAJ-1: OutputFormatter.emit_error() writes to stdout instead of stderr

**File:** `src/foundry_cli/common/output_formatter.py`, lines 226-233
**ADR Violation:** ADR-004 states "Error output always goes to stderr"

```python
# Lines 226-233 — CURRENT (INCORRECT):
def emit_error(self, error_data: Dict[str, Any]) -> None:
    """Format and emit error data to stdout."""  # Docstring says stdout!
    output = self.format_error(error_data)
    sys.stdout.write(output + "
")   # ← WRONG: should be sys.stderr
    sys.stdout.flush()
```

**Issue:** The docstring says "stdout" and the implementation writes to `sys.stdout`. ADR-004 explicitly requires error output on stderr. This is a correctness bug that affects the CLI contract.

**Fix:** Change `sys.stdout` to `sys.stderr` in both `write()` and `flush()` calls; update docstring to say "stderr".

### MAJ-2: ErrorSerializer uses internal placeholder exception classes not mapped from actual SDK

**File:** `src/foundry_cli/common/error_serializer.py`, lines 59-90
**ADR Violation:** ADR-001 states "SDK `PalantirRPCException` subclasses must be mapped"

```python
# Lines 59-90 — Internal placeholder classes defined but never match real SDK exceptions:
class _SDKAuthError(Exception):
    """SDK authentication failure."""

class _SDKValidationError(Exception):
    """SDK validation failure."""
# ... 5 more internal classes ...
```

**Issue:** The `_SDK*Error` classes are internal placeholders. The actual `foundry-platform-python` SDK raises `PalantirRPCException` subclasses. The MRO-based matching in `serialize()` will never hit these internal classes. The HTTP status code classification provides a fallback, but the primary exception mapping is dead code.

**Fix:** Import and map actual SDK exception types from `foundry_platform_python`, or document that HTTP status classification is the primary path.

### MAJ-3: RetryHandler has unused import of LogSetup — circular dependency risk

**File:** `src/foundry_cli/common/retry.py`, line 31

```python
# Line 31 — Unused import:
from foundry_cli.common.log_setup import LogSetup
```

**Issue:** `LogSetup` is imported but never referenced in the module. This creates circular dependency risk and may trigger logging configuration at import time.

**Fix:** Remove the unused `from foundry_cli.common.log_setup import LogSetup` import.

### MIN-1: retry.py — `_calculate_delay` returns `Any` from type checker perspective

**File:** `src/foundry_cli/common/retry.py`, lines 83-116

**Issue:** Type checker reports: "Returning Any from function declared to return 'float'" on `delay *= jitter_factor`.

**Fix:** Use `float(delay * jitter_factor)` to ensure the return type is `float`.

### MIN-2: ErrorSerializer error envelope includes full traceback — sensitive data exposure risk

**File:** `src/foundry_cli/common/error_serializer.py`, lines 199-201

**Issue:** Full traceback string in JSON error envelope may contain file paths, internal structure, or environment details. OWASP A02 consideration.

**Recommendation:** Consider a `--no-traceback` flag or env var to suppress in production. Not a blocker.

### MIN-3: LogSetup._configured class variable not thread-safe

**File:** `src/foundry_cli/common/log_setup.py`, lines 103 and 138

**Issue:** `_configured` flag is a plain class variable without locking.

**Recommendation:** Add threading lock. Low priority for CLI-only usage.
