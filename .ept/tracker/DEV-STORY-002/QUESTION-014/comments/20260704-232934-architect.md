# Architect Decision — QUESTION-014

## Decision

**Option (a): Update the DEV-STORY-002 AC to remove the file-output and rotation requirement; align the AC with ADR-005 (NDJSON on stderr only).** File-based logging, if ever needed, is deferred to a separate operations-focused story. Reject options (b) and (c) for v1.

## Rationale

1. **ADR-005 is unambiguous and the implementation correctly follows it.** ADR-005 §Decision: "Log format: Newline-delimited JSON (NDJSON) **on stderr**." ADR-005 §Alternatives explicitly **rejected** file logging: "Structured logs to a file | Would require a log file path config; adds complexity; orchestrators already capture stderr." The implementation (`log_setup.py`) conforms: stderr handler, JSON formatter, no `FileHandler`/`RotatingFileHandler`.
2. **The file/rotation requirement originates only in the DEV-STORY-002 AC**, not in any SRS FR or customer-confirmed source. Searching SRS-001 found **no** `FR-LOG*` requirement and **no** customer-facing requirement for file logging or rotation. It is an AC elaboration that contradicts an Accepted ADR.
3. **Per the project's ADR governance, Accepted ADRs override AC elaborations.** ADRs are architectural decisions ratified by the Solution Architect; ACs operationalize them but cannot contradict them. When an AC and an ADR conflict on an architectural concern (logging topology), the ADR wins and the AC is corrected.
4. **Option (b) (update ADR-005 to add file/rotation) is wrong for v1** because:
   - It reverses a rationale already documented ("orchestrators already capture stderr") without new evidence.
   - It introduces a config surface (`log_path`, rotation size, retention) with no customer requirement driving it — YAGNI violation.
   - Containerized/CI deployments (the primary v1 target per DEVOPS-003) handle persistence via container log drivers, not in-process file handlers.
5. **Option (c) (split into a separate NFR story) is partially correct and is the deferral mechanism.** I am adopting it as a **follow-up**, not as the resolution to this conflict: the v1 AC must still be corrected now to unblock TESTCASE-001. A separate story can revisit file logging when a concrete deployment scenario demands it.

## Sub-decisions / Caveats

- **Air-gap / on-prem persistence:** If a future on-prem customer requires persistent log files (e.g. for SIEM ingestion where stderr capture is unavailable), that need should be captured as a new NFR-OBS-* story and routed through a fresh ADR (e.g. ADR-005-amendment or ADR-008) — not retrofitted silently into DEV-STORY-002.
- **`call_id` correlation (ADR-005 §Rationale) provides the observability bridge** across stderr capture, stdout metadata, and error envelopes. File logging is not required for invocation tracing.
- **External rotation:** Container orchestrators (K8s, Docker, systemd) already provide log rotation for captured stderr. Adding in-process rotation duplicates platform capability.
