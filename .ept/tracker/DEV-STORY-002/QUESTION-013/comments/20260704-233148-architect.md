# Architect Correction — QUESTION-013 (supersedes prior decision)

## Status of this comment

**This comment CORRECTS and SUPERSEDES my prior decision comment (20260704-232839-architect).** The prior decision was based on incomplete research and reached the wrong conclusion. I am flagging this transparently rather than leaving the erroneous decision standing.

## Error in the prior decision

My prior comment claimed: *"The separator is not in any upstream contract."* **This is wrong.** I missed two pieces of evidence during the QUESTION-013 research:

1. **ADR-005 §Decision (line 62):** "A separator comment line `# ---metadata-start---` precedes the metadata JSON object so parsers can distinguish NDJSON log lines from the metadata object."
2. **ADR-005 §Consequences (line 84):** "The metadata emitter **must** write the separator `# ---metadata-start---` before the metadata JSON object on stderr."
3. **ADR-005 §Rationale:** The separator has an explicit purpose: "Prevents log+metadata confusion; orchestrators that look for the metadata object can scan for the separator."
4. **`src/foundry_cli/common/log_setup.py`:** already declares `METADATA_SEPARATOR = "# ---metadata-start---"` as a module constant per ADR-005 — confirming the separator is part of the implemented contract surface.

I also misjudged the JSON-validity concern: the separator is a **separate line** preceding the JSON object, not embedded inside it, so `json.loads()` per-line parsing of subsequent lines is unaffected. The "JSON does not support comments" objection does not apply.

## Revised Decision

**Option (a): Add the `# ---metadata-start---` separator emission to `OutputFormatter.emit_to_stderr()`.** The implementation is the non-conformant artifact, not the AC. ADR-005 is the authoritative contract; the DEV-STORY-002 AC correctly reflects ADR-005; the bug is in `output_formatter.py`.

## Rationale (corrected)

1. **ADR-005 is Accepted and explicit** — the separator is a documented mandatory behavior, not an AC elaboration. Accepted ADRs override implementation convenience.
2. **The separator has real architectural purpose** — stderr carries BOTH NDJSON log lines AND a final metadata JSON object (per ADR-005 §Context: "The log format must not collide with the structured metadata JSON object emitted to stderr on success"). Without the separator, consumers cannot reliably tell where logs end and metadata begins on stderr.
3. **The constant is already defined** in `log_setup.py` (`METADATA_SEPARATOR`) — `output_formatter.py` simply fails to use it. This is a clear implementation omission, not a design ambiguity.
4. **The prior option (b) reasoning ("stream separation already disambiguates") was wrong** — it conflated stdout/stderr separation (payload vs metadata, per FR-OUT-1/FR-OUT-2) with the within-stderr ambiguity (NDJSON logs vs metadata JSON). ADR-005 §Context explicitly states the collision risk is *within stderr*, between logs and metadata.
5. **Options (b) and (c) from the prior comment are retracted.**
