# Architect Decision — QUESTION-013

## Decision

**Option (b): Drop the `# ---metadata-start---` separator requirement from the DEV-STORY-002 AC. Keep the implementation as-is (pure JSON to stderr).** Reject options (a) and (c).

## Rationale

1. **The separator is not in any upstream contract.** I searched SRS-001 and ADR-004:
   - **FR-OUT-2** (the governing requirement): "Pagination metadata SHALL be emitted to stderr as **compact JSON**" — specifies JSON only, no separator.
   - **FR-PAG-2:** "emitted to stderr as part of the metadata JSON object" — same.
   - **ADR-004 §Special cases:** "Pagination metadata on stderr | Always JSON (never TOON, always stderr)" — JSON only.
   - **NFR-IFACE-2:** "diagnostics and metadata on stderr" — no separator.
   The separator is an AC elaboration with no source in customer-confirmed requirements (Q&A R1: A4.1 / R2: A(Q2(R2).3-C) never mention it).
2. **The separator actively harms strict JSON consumers.** Pagination metadata is required to be JSON. A `# ---metadata-start---` comment line is **not valid JSON**; any consumer that does `json.loads(stderr_line)` on the first line breaks. JSON does not support comments. Adding the marker would violate FR-OUT-2's "compact JSON" wording.
3. **Stream separation already disambiguates.** FR-OUT-1 (stdout = primary result) and FR-OUT-2 (stderr = metadata) keep payload and metadata on different OS streams. The separator's only purpose would be to help consumers that merge streams (`2>&1`) — but merging is explicitly contrary to the CLI contract (DCC-4, NFR-IFACE-2). Building contract features to support anti-pattern usage is bad architecture.
4. **Option (a) (add separator to impl) violates FR-OUT-2** by emitting non-JSON on a JSON-mandated stream. Rejected.
5. **Option (c) (flag-gated separator) doubles the test matrix** for a feature no upstream requirement demands. It also pushes a contract-compatibility decision onto every caller (which flag value?). Rejected as over-engineering.

## Sub-decisions / Caveats

- **If a future use case needs stream-merge disambiguation** (e.g. a debug mode that pipes `stdout+stderr` to one log), the correct solution is a separate `--debug-merge` CLI flag that wraps both streams in an outer envelope — not a comment marker polluting the stderr contract. That is a separate feature request, not this AC.
- **Logging on stderr (per ADR-005) vs metadata JSON on stderr:** these coexist on stderr. The separator was perhaps intended to distinguish NDJSON log lines from the single metadata JSON line. The cleaner solution is **temporal ordering** (metadata JSON emitted last, after all log lines) plus a documented contract that "the last non-empty stderr line is the metadata JSON object when pagination occurred." This belongs in ADR-005 as a clarification, not as a per-line marker.
