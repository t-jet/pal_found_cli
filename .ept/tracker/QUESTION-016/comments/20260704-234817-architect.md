# Architect Decision — QUESTION-016 (Invalid JSON args → wrong exit code)

## Research done
- Read TESTCASE-003 §Discrepancy D-2 and TC1.7 / TC5.7 (both expect exit 6 today, flagged as wrong).
- Read implementation L177-184, L235-238: `json.loads(...)` is invoked inside `_invoke` and any `JSONDecodeError` (subclass of `ValueError`) propagates up to `except Exception` (L447) → `EXIT_SERVER_ERROR` (6).
- Read ADR-001 §Decision: exit 1 = UserInputError for "Invalid CLI arguments, validation failure, missing required parameter". ADR-001 §Consequences: "All error handling in `_foundry_cli_common.py` must map SDK exceptions to these codes" — note: argument *parsing* failures are explicitly user-input, distinct from SDK/server errors.
- Searched ADRs 001-007: none classify malformed CLI-provided JSON as a server error. The intent of ADR-001 row 6 (ServerError) is "API returns 5xx / SDK internal error" — a JSON typo in a CLI flag is not an API failure.

## Decision
**(b) Update implementation.** Malformed JSON supplied via `--dataset-r`, `--schema`, `--backing-datasets`, `--primary-key` MUST return **exit 1 (UserInputError)**, not exit 6. ADR-001 stands as written and is the authority.

## Why
- **ADR-001 is unambiguous**: argument validation failures map to exit 1. The current behavior violates the contract.
- **Error provenance**: `JSONDecodeError` originates from the user's command line, not from the Foundry API or SDK. Reporting it as `ServerError` (6) misleads orchestrators into thinking the API is failing, prompting retries instead of fixing the input.
- **Agent UX**: An agent that sees exit 1 with a clear "invalid JSON in --schema" message knows to re-prompt the user; exit 6 invites useless retries against a healthy server.
- **Fix is small and surgical**: wrap the four `json.loads(...)` call sites in try/except and re-raise as `ValueError("--<flag> must be valid JSON: <detail>")` after the access-control check but before `_invoke`. The generic `except ValueError` (or explicit handler) returns `EXIT_USER_INPUT`.

## Required actions (developer — defer to follow-up BUG-SUB)
1. **File as BUG-SUB-005** under DEV-STORY-005 (qa-engineer or developer to create), linking this QUESTION as the source. AC for the bug:
   - Given `--schema 'not json'`, when the CLI runs `dataset put-schema`, then stderr contains a `UserInputError` envelope and the process exits 1.
   - Same AC for `--dataset-r`, `--backing-datasets`, `--primary-key`.
2. **Implementation guidance**: in `_invoke`, wrap each `json.loads(...)` call:
   ```python
   try:
       rids = json.loads(rids_arg) if isinstance(rids_arg, str) else rids_arg
   except json.JSONDecodeError as e:
       raise ValueError(f"--dataset-r must be valid JSON: {e}") from e
   ```
   Add an `except ValueError as exc:` handler in `main()` (before the generic `except Exception`) that calls `ErrorSerializer().serialize(exc)` and returns `EXIT_USER_INPUT`.
3. **Update TESTCASE-003** TC1.7 and TC5.7 expected column from `exit 6` to `exit 1` once the bug is fixed.
4. **Cross-skill consistency**: this pattern should be applied to all 21 CLI skills (open follow-up audit if other skills use the same `json.loads` inline pattern). Out of scope for this QUESTION — flag as a separate ticket if found.

## Resolution
QUESTION-016 → Resolved. Decision is "implementation must conform to ADR-001". Defect is to be filed as a BUG-SUB under DEV-STORY-005 by the requester (qa-engineer) or developer.
