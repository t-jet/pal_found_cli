## Research Done

Reviewed SRS-001 FR-OUT-3 and FR-DL-1 through FR-DL-3, SAD-001 `BinaryDownloadHandler` and binary download sequence, TESTCASE-003 D-6, and `foundry_datasets_cli.py` file operations. Links checked: this question blocks DEV-STORY-005 and asks about TESTCASE-003.

## Answer

Binary download handling is required for operations that return binary file content. For datasets, that means `file content`; `file get` remains metadata unless the SDK returns bytes for that operation.

Required behavior for binary content:
- Add CLI `--download-path` override and keep `FOUNDRY_AGENTIC_CLI_DOWNLOAD_PATH` default `.foundry-data/downloads`.
- Write content under `{download_path}/{uuid}/{original_file_name}`.
- Normalize and validate the resolved output path so it stays under the configured download root.
- Enforce `FOUNDRY_AGENTIC_CLI_MAX_DOWNLOAD_BYTES` default `1572864`.
- If content is larger than the limit, write only up to the limit, set `truncated=true`, and still return exit 0 unless the SDK/read itself fails.
- Stdout must be a JSON envelope with `file_path`, `file_size`, `checksum_md5`, `checksum_sha256`, `mime_type`, and `truncated`.
- Diagnostics and pagination/download metadata stay on stderr.

## Resolution

QUESTION-020 is answered. TESTCASE-003 should test `file content` binary envelope and max-byte behavior. It should not force disk writing for `file get` if that operation is metadata-only in the SDK.
