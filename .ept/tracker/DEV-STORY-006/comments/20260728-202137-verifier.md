### Technical scope and constraints

1. Pattern reuse: The filesystem CLI mirrors the DEV-STORY-005 foundry-datasets namespace-skill pattern (thin async wrapper over SDK clients). The more recent DEV-STORY-007 foundry-ontologies pattern (OP_SPECS-based operation table) is also available as a refinement reference; the implementer should follow whichever the Tech Lead selects during Grooming DESIGN.
2. Resource.Role nesting: resource-role operations (add, list, remove) are accessed via client.Resource.Role, not a top-level property. The _get_client dispatcher must return client.Resource.Role for the 'resource-role' resource name.
3. Paginated operations: five ops return AsyncResourceIterator/ListResponse and require PaginationHelper wiring with page_size, page_token, and batch-pages aggregation: (folder, children), (project, organizations), (resource, markings), (resource-role, list), (space, list).
4. RID and path addressing: resource operations support both RID-based (get, get_batch) and path-based (get_by_path, get_by_path_batch) lookups; the get_by_path signature is keyword-only (path argument).
5. Error coverage: SDK error classes include FolderNotFound, ResourceNotFound, PathNotFound, InvalidPath, InvalidFolder, PermissionDenied variants, GetRootFolderNotSupported, GetSpaceResourceNotSupported. ErrorSerializer must map these to ADR-001 exit codes (4 NotFound, 3 PermissionDenied, 1 UserInput).
6. Deployment target: standard namespace-skill package under .claude/skills/foundry-filesystem/ (SKILL.md + scripts/foundry_filesystem_cli.py) plus a console entry point (foundry-filesystem) in pyproject.toml.
