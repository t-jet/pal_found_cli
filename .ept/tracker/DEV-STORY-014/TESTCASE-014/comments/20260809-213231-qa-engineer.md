## QA test case design plan

### Objective
Design an executable, traceable QA test-case suite for DEV-STORY-014 covering all 20 foundry-orchestration operations and every story acceptance criterion, matching the canonical TESTCASE-010/011/012/013 structure.

### Scope
- Catalog/parser/help for all 20 commands; exact nested SDK routing (Build, Job, Schedule, ScheduleVersion; ScheduleRun sub-client has 0 public methods and must NOT appear in OP_SPECS).
- JSON argument validation (build.create target/fallback-branches, schedule.create and schedule.replace action/trigger/scope-mode) before client creation.
- Exactly 3 cursor-paged commands via PaginationHelper (build.jobs, build.search, schedule.runs); batch get_batch and SearchBuildsResponse single-call; no invented pagination elsewhere.
- No binary downloads in this namespace (BinaryDownloadHandler not required).
- AccessControlGuard precedence: global → namespace → operation; read-only blocks the 8-op write set (build.cancel, build.create, schedule.create, schedule.delete, schedule.pause, schedule.replace, schedule.run, schedule.unpause); semantic reads despite POST (build.search, schedule.get_affected_resources).
- Metadata-only tier exact 12 permitted / 8 blocked; fail closed on missing/malformed packaged policy.
- include_attribution=False; B3 tracing enabled/disabled/retry-stable/restore; no W3C.
- Retry behavior: transient-only, cursor-local state, at-least-once disclosure for mutating ops.
- ADR-001 error taxonomy, ADR-002 timeouts, ADR-004 output formats (json/toon/auto), ADR-005 NDJSON stderr, privacy/confidentiality.
- Packaging: console entry point, Claude skill launcher, wheel/editable installs from arbitrary CWD, entry-point preservation, regression gates (Python 3.11/3.12, ruff, mypy, bandit, >=80% coverage).

### Approach
- One scenario per distinct behavior path in Given/When/Then format, with Type labels (positive, negative, boundary, security, resilience, structural, packaging) and smoke/environment labels consistent with siblings.
- Each case defines: command/function under test, prerequisites/fixtures, steps, expected stdout/stderr/exit code, filesystem effects, cleanup, evidence mapping to DESIGN-014 and story ACs.
- A traceability matrix maps every story AC to one or more test cases.
- Deliverable: .ept/docs/deliverables/qa/TESTCASE-014-test-cases.md; document_index.md updated.
- Evidence: this plan comment, the case-set comment, and registration in the document index. No live Foundry service access; mocked SDK fakes for routine evidence with optional approved non-production smoke.

### Review
- Tech lead reviews the completed case set and records approval before TESTEXEC-014 starts (per sibling pattern).
